# Leaf 分支与功能文档规范

生效日期：2026-11-03。参与 Leaf 开发的维护者和 agent 在创建分支、实现功能、整合和发布前必须阅读本规范。规范在 `main` 维护；旧分支文档与本规范冲突时，以 main 上的最新规范为准。当前状态见 [LEAF_STATUS.md](LEAF_STATUS.md)。

## 1. 分支流向

新增功能及功能修复必须遵循：

```text
当前分支的已核实 HEAD
  └─ 新功能分支 feature/<主题> 或 fix/<主题>
       └─ 下一小版本预备分支 release/leaf-X.Y.Z
            └─ PR → main
```

每个新功能单独建分支，不能直接在当前分支、版本预备分支或 main 上开始实现新功能。功能必须先整合进版本预备分支，完成该版本的验证和文档汇总，再由预备分支通过 PR 合入 main；不得把功能分支直接合入 main，也不得在预备分支整合后另开功能到 main 的旁路。

本项目这里的“下一小版本”指当前版本序列的下一个修订号，例如 main 为 `1.19.2` 时使用 `release/leaf-1.19.3`；不是自动升级到 `1.20.0`。有用户明确指定的下一版本时，以该版本为准。创建预备分支本身不表示修改版本元数据或发布。

## 2. 开始一个功能

1. 核对当前分支、HEAD、工作区修改、tracking upstream，以及远端 main 的版本和已有预备分支。记录实际起点，不能擅自切到 main 来替代用户当前分支基线。
2. 从当前分支已核实的 HEAD 新建功能分支。工作区有未提交修改时，先识别归属；保留无关修改，不擅自 stash、提交或带入新功能，必要时从该 HEAD 建独立 worktree。
3. 检查本地和远端是否已有下一小版本的 `release/leaf-X.Y.Z`。存在则复用；只有远端存在时，使用该远端分支的实际提交建立本地工作入口，不从 main 另造同名历史。不存在时，从核实过的最新 main 建立预备分支，并建立版本准备文档。创建功能分支时就完成这项检查，不推迟到合入阶段。
4. 在功能分支开始实现前，创建 `docs/features/<主题>.md`，写明本次要实现的功能、验收条件和待办，并在开发计划中登记该功能文档入口。已有能完整覆盖这些内容的专题文档可以复用，但必须在开发计划中链接，不能只放在会话或本地任务目录里。
5. 开发中随进度更新该功能文档，区分“计划实现”“已实现”“已验证”和“待处理”。不要把待办提前写成已完成。

分支创建与文档初始化属于同一个开工步骤。初始化功能文档至少包含：

```markdown
# <功能名称>

- 功能分支：feature/<主题> 或 fix/<主题>
- 创建基线：<原分支>@<完整 commit>
- 目标预备分支：release/leaf-X.Y.Z
- 状态：计划中 / 实现中 / 待整合 / 已整合

## 功能与范围
<解决的问题、预期行为、验收条件>

## 已实现
<初始写“尚未实现”，之后按实际进展填写>

## 待办
- [ ] <实现项>
- [ ] <对应验证项>
- [ ] 整合至预备分支并更新版本功能与待办汇总

## 验证与边界
<实际验证结果、对应提交、证据链接和未验证范围>
```

## 3. 功能合入预备分支

合入前检查功能分支相对目标预备分支的完整差异。功能分支继承了其他未整合功能时，也必须明确列出依赖和随此次合入的内容，不能只描述最后一次修改。

功能代码和对应专题文档一起进入预备分支。每次功能合入后，必须在同一次整合收尾中更新该版本的准备文档 `docs/LEAF_X_Y_Z_PREPARATION.md`、[当前状态](LEAF_STATUS.md)和[开发计划的功能／待办](LEAF_DEVELOPMENT_PLAN.md#7-待办与验证)。仅保留功能分支文档、只添加链接而不汇总状态，或等到发版时再补记，都不算整合完成。

版本准备文档必须包含以下内容，可合并同类条目或追加，不能覆盖丢失其他功能的记录：

| 内容 | 必须记录 |
| --- | --- |
| 已整合功能 | 功能名称、实际行为、源分支、源提交、整合提交或 PR、功能文档链接 |
| 验证情况 | 功能分支的验证和版本整合后的验证分别记录，附结果及证据 |
| 剩余待办 | 未完成实现、必要验证、已知问题，以及归属功能；没有则明确写“无” |
| 调整记录 | 延后或取消的事项及原因，不能静默删除，也不能把取消记为通过 |

同一事项合并去重，完成的待办移入已实现或已验证记录，未完成的继续保留。标注“已整合到预备分支”不等于“已合入 main”或“已发布”。

## 4. 预备分支合入 main

向 main 发起 PR 前，确认计划纳入的功能均已进入预备分支，功能／待办文档已汇总，要求的验证已完成，未解决事项已明确处理。PR 说明列出本版本功能、实际验证和保留的待办。

由 `release/leaf-X.Y.Z` 向 main 发起 PR，并遵守现有 main 保护与 CI。合入时把对应版本的已实现功能和剩余待办一并带入 main，更新长期状态入口；保留前期已发布功能，不能用版本分支的旧文档覆盖 main 的新规范或其他进展。合入 main 与发布是两个状态，只有正式发布成功后才标为“已发布”。发布操作见 [LEAF_BUILD.md](LEAF_BUILD.md)。

## 5. 纯文档维护

沿用纯文档维护约定：只更新规范、待办、已有功能说明等文档时，可以新建 `docs/<主题>` 分支直接通过 PR 合入 main，不必经过版本预备分支。文档与功能代码一起修改时必须走功能 → 预备分支 → main 的流程，不能使用此例外。

轻量 CI 只适用于根 README 和 `docs/`、`doc/` 下 Markdown；`CHANGELOG.md`、其他路径及混合改动仍按 [CI 范围规则](LEAF_1_19_3_PREPARATION.md#main-保护与-ci)执行。文档例外不允许直接 push main。

本规范是开发与合入时必须遵守的流程；现有 GitHub 保护强制 PR 与检查，但尚未自动校验“功能先入预备分支”的分支流向。维护者和 agent 在发起及合并 PR 时必须核对该条件，不能把 CI 通过视为已检查分支流向。

## 6. 当前版本落点

截至 2026-11-03，main 版本为 1.19.2，下一版本预备分支 `release/leaf-1.19.3` 已存在，直接复用。圆圈修复 `fix/leaf-viewed-marker` 保持独立；后续整合时须先收进该预备分支，并把已有修复说明、验证和剩余待办纳入 [1.19.3 准备记录](LEAF_1_19_3_PREPARATION.md)，之后才能由预备分支合入 main。本次制定规范不代表已执行该整合。
