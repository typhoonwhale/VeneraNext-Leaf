# Leaf 应用内更新实施与验证

2026-10-26，开发分支 `feature/leaf-in-app-update`，实施基线 `c93eee1`，开发版本 `1.18.3+241`（ARM64 versionCode `2412`）。本次不创建标签或发布 Release，公开版本仍为 1.18.2。需求以[正式方案](LEAF_IN_APP_UPDATE_DESIGN.md)为准。

## 已实现

“关于 → 检查更新”取得同一 GitHub Release 的版本、说明和唯一 ARM64 APK，校验上传状态、大小、SHA-256 和下载地址；下载完成后进一步校验真实内容、Android 包名、签名、版本和 ABI。随后由用户授权未知来源安装，并在系统安装器确认。Debug 不开放正式包原位更新，其他平台保留发布页流程。

唯一应用级控制器负责 `cacheRoot/updates/`：不续传、失败从零重试、取消等待传输与文件句柄收尾、启动删除半包。它在初始化后独立执行恢复，不依赖启动检查开关或联网。正常漫画缓存仍由 `CacheManager` 管理 `cacheRoot/cache/`；导入、分享等调用使用各自临时子目录，未发现新增更新目录被既有全根清理覆盖的链路。

原生安装记录独立保存于 SharedPreferences，使用 attempt ID 和进程身份关联 ActivityResult。结果未知时保留唯一完整包；即使系统回收 APK，原生未结束的占用仍阻止重下与覆盖。只有实际系统包身份和版本达到目标，或对应安装明确取消/失败，才释放占用；权限页与安装器往返不会误删 APK。

- 新下载与安装控制器 20 项回归包含真实临时文件和流式响应：取消时序、重复点击、头响应/流无数据超时、损坏/超长包、重启恢复、目录哨兵和符号链接，以及未知安装占用与 APK 回收。
- 纯 JVM 原生策略 4 组验证通过：固定路径与符号链接、ARM64/重复库约束、回调关联、终态占用规则。它不替代 Android PackageManager 和 Activity 的设备验证。
- 指定 15 个 Dart 实现/测试文件静态分析无问题；格式、结构导入、架构清单及 Git 空白检查通过。
- 实际回读 GitHub 1.18.2 资产，再用新候选模型解析通过：现有 `Leaf-1.18.2-2402-release-arm64-v8a.apk`、23,377,803 字节、SHA-256 `3e02832b4f4bdb1a314447dbd921f10e5f7cec5bf14293f28a0b63ffa0403c5b`。没有上传或替换资产。

## 待 Leaf5+ 实测

本机未连接设备，不宣称完成真实覆盖升级、Android 权限往返、进程被系统终止后的安装结果回调，或数据保留实测。也未运行全仓 Flutter 测试集；已有宿主/原生依赖限制不在本次功能范围内。

1. 手动覆盖安装首个承载功能的固定签名 Release，确认原收藏、阅读记录、设置仍在；不要卸载旧版。
2. 本仓库出现更高版本后，检查说明和大小，测试下载取消、网络断开及重试；失败应清除半包，重启不续传。
3. 测试未知来源授权的允许/拒绝、系统安装取消/成功；成功后再次打开应用，专用更新目录应清空。
4. 安装器打开时切回应用或结束进程，再启动核对保护状态；无法确认结果时应保留候选并给出发布页入口。手动安装同签名目标或更高版后，离线启动且自动检查关闭也应完成清理。

本功能不更改漫画数据库、数据迁移或备份格式。首次手动安装后，仍需要一个正式发布且版本更高的包，才能在设备上验收完整内置更新链路。
